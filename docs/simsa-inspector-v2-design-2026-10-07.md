# Simsa 검사 엔진 v2 — 증거 고리 설계 (2026-10-07)

> 근거: Bae 2026-10-07 — "최상급 모델로 만들어도 한번에 결과물이 안 나오는 게 문제. 그래서 conclave를 만들었고, 그게 안 되니까 simsa로 간 것." · "새로 설계해서 작동하게 만들어. 비용은 계산해서 부과하면 된다."
> 상위 문서: `docs/simsa-prd.md`, `docs/simsa-si-tier-design-2026-09-24.md`(주소 → 역추론 → "맞나요?" → 확인된 must = 정답지), `docs/simsa-strategy-2026-10-05.md`.
> 실측 배경: v1(agent) 프로덕션 — 미용실 6앱 짚음 0→46→31%, 처음 보는 파일럿 7앱 2/5 · 404 앱은 검사 중단 · 소개 문구로 must 통과 · 의도 불일치(Bolt 자가 점검표) 놓침. **같은 엔진을 강한 모델로만 돌려도(2026-10-07 로컬) Bolt 불일치는 그대로 놓침 → 원인은 모델이 아니라 설계.** 반면 Claude가 같은 13앱을 손으로 검증했을 때 결함을 전부 찾았다 — 그 방법을 제품으로 옮기는 것이 v2다.

## 0. 원칙 — 의견이 아니라 관찰된 사실의 고리

1. **어떤 모델도 한 번에 맞히지 못한다.** 빌더가 한 번에 작동하는 앱을 못 만드는 것과 같은 이유로, 검사도 한 번의 판단으로는 틀린다. Conclave(실행 없이 모델 의견을 겹침)와 v1(모델이 한 번 보고 판단 + 두 번째 의견)이 같은 함정에 빠졌다.
2. **고리를 끊는 것은 더 좋은 모델이 아니라 외부 기준 = 실제 실행 결과다.** 판단은 항상 *가설 → 실행 → 관찰 → 수정*을 확신이 설 때까지 반복한다.
3. **모든 판정은 관찰된 증거물(artifact)을 인용해야 유효하다.** 증거물 = 네트워크 요청 기록, 저장소 내용, 소스·번들 코드 조각, 다른 브라우저·역할에서 본 화면, 콘솔 오류, 조작 전후 화면 차이. 모델의 서술("그래 보인다")이나 **앱 화면의 소개 문구는 증거가 아니다.**
4. **제품도 같은 고리다.** Simsa가 증거로 짚음 → 빌더팩·고친 파일·자동 수정 → 재배포 → 같은 계획으로 재검사 → 통과할 때까지 반복. 최종 성공 기준은 "엔진이 맞혔는가"가 아니라 **"고리가 앱을 작동하게 만들었는가"**다.

## 0.5 단순 QA 도구와의 차별점 — v2가 반드시 지켜야 할 것 (Bae 2026-10-07)
QA 자동화·테스트 생성 도구(Momentic·Autonoma·Shiplight 등)와 빌더 자체 테스트(Lovable·Replit)는 "버그가 있는가"를 본다. Simsa는 아래 다섯 가지로 다르며, v2 설계·평가·출력 전부가 이것을 따른다.

| # | 차별점 | v2에서의 의무 |
|---|---|---|
| X-1 | **원래 원한 것 기준의 판정** — 버그 목록이 아니라 "의도대로 작동하는가" | 판정 단위는 언제나 유저가 확인한 의도·must 기준. 일반 버그(콘솔 오류 등)는 의도에 영향을 줄 때만 판정에 반영. **의도 불일치("생각과 달라요")를 독립 판정으로** 낸다(V-7) — 일반 QA 도구는 이걸 못 본다 |
| X-2 | **비개발자·비영어권** — 한국어(현지어) 쉬운 말, 개발 용어 없이 | 리포트·이유·고치기 지시 모두 비개발자 언어(KO/EN). 증거물은 접어 두고 "무엇이 안 되고 왜"를 먼저. 현지 실데이터(한글 이름·번호·KST)로 검사 |
| X-3 | **찾는 데서 끝나지 않고 고친다** — 빌더팩·고친 파일·자동 수정 PR | 실패마다 고치기 결과물(F 단계)이 필수 출력. 원인은 소스 근거. "보고서만 주는 QA"가 되지 않는다 |
| X-4 | **작동할 때까지 도는 고리** — 같은 기준으로 재검사해 통과까지 | 계획을 저장해 재검사에 그대로 재사용(L 단계). 성공 지표는 "고리가 앱을 작동하게 만든 비율"(G4) |
| X-5 | **빌더 밖의 독립 심사관 + 빌더별 실패 지도** | 만든 모델이 채점하지 않는다. 런마다 빌더 지문 × 결함 분류 기록(C13) 유지 |

평가에 반영: G1~G3에 **의도 불일치 탐지**(파일럿 Bolt 자가 점검표·ChatGPT 고정 결과처럼 "만든 것 ≠ 원한 것")를 별도 지표로 둔다 — 알려진 불일치의 80% 이상을 증거와 함께 짚을 것. 리포트 문구는 비개발자 감사(journey-audit 개발 용어 0)를 통과할 것.

| V-2 | pass는 **상태 변화 증거물**(쓰기 요청 2xx·저장소 변화·조작 전후 DOM 차이·다른 브라우저에서 관찰)이 있어야 한다. 화면 글자·소개 문구만으로 pass 금지 | [LOCKED] |
| V-3 | fail은 **새 브라우저에서 독립 재실행으로 같은 증거물이 다시 나와야** 확정. 우리 입력 탓 오류는 입력을 고쳐 재시도 | [LOCKED] |

| V-6 | 비용 = 런마다 정확히 기록 + 청구 예상액(원가 × 마진) 표시. **실제 결제는 별도 승인 전까지 꺼짐** | [LOCKED] |

| V-8 | 출시 = `engine:"agent_v2"` 장비 키 전용, v1은 대체 경로로 유지. 공개는 13앱 평가 + 새 주제 벤치마크 통과 후 | [LOCKED] |

## 2. 구조

```
Worker(오케스트레이터) ── 런 생성·예산·증거물 저장(R2/D1)·LLM 프록시(키는 서버에만)
   │
   └─ 검사 컨테이너(Playwright) ── 에이전트 고리(네이티브 함수 호출)
          도구: 브라우저 조작 · 관찰(접근성 트리 + 스크린샷) · 네트워크 기록 · 저장소 덤프
                · 소스/번들 읽기·검색 · 콘솔 · 새 브라우저(다른 손님·기기) · 시계·시간대 · 화면 폭
          모든 도구 호출 → 증거물(id 부여, 원문 보관) → 판정은 증거물 id로만 인용
```

### 2.1 증거물 저장소 (가장 먼저 만든다 — 나머지 전부의 토대)
- 런마다 `artifacts[]`: `{id, kind(request|storage|source|screen|console|diff|context), at, summary, raw(잘라서 보관)}`.
- 판정 스키마: `{acId, verdict: pass|fail|not_verified|mismatch, claim, artifactIds[]}`.
- **기계 검증기**(LLM 없음): ① artifactIds가 비면 강등 ② 인용한 증거물에 claim의 핵심 값(예: "요청 0건", 저장 키 이름, 오류 문구)이 실제로 있는지 문자열 대조 ③ pass는 상태 변화 종류의 증거물 1개 이상(V-2) ④ fail은 재현 증거물 쌍(V-3). 검증기를 통과하지 못한 판정은 리포트에 오르지 않는다.

### 2.2 고리 단계
1. **정찰(R)** — 주소를 연다. 열리지 않음·404·`index.html` 없음 → 즉시 *고장*(원인 + 증거물). 화면을 둘러보고(관찰된 링크만 따라감), HTML·JS 번들을 받아 **정적 사실**을 뽑는다: 외부로 나가는 요청 대상(서버·Supabase·API), 저장소 사용(localStorage·IndexedDB), 결과가 계산되는지 하드코딩인지(고정 배열·난수·입력 미사용), 설정 자리표시자(`YOUR_SUPABASE_URL` 등), 날짜 처리(`toISOString().slice(0,10)` 같은 UTC 날짜).
2. **가설(H)** — 정적 사실 + 확인된 의도에서 *위험 목록*을 만든다: 데이터가 기기에만 남음, 결과가 가짜, 서버 연결 누락, 역할 화면 없음, 시간대 날짜, 의도와 다른 기능. 각 가설에 "무엇을 하면 무엇이 관찰되어야 참/거짓인가"를 적는다.
3. **계획(P)** — QA 엔지니어처럼: must 기준마다 끝까지 해 보는 경로 + 가설마다 확인 실험(입력을 바꿔 결과가 바뀌는가, 새 브라우저에서 보이는가, 관리 화면에 나타나는가, 시계를 00:30 KST로, 오류 경로). 계획도 증거물로 남긴다(재검사 때 그대로 재사용).
4. **실행(E)** — 최상급 모델이 도구로 조작하고, 관찰할 때마다 가설을 갱신한다. 화면이 안 바뀌면 같은 행동을 반복하지 않고 다른 경로를 찾는다. 지어낸 주소는 열지 않는다.
5. **확인(V)** — 판정 후보마다 독립 재실행(새 브라우저)으로 같은 증거물을 다시 얻는다. pass·fail 모두.
6. **판정(J)** — 기계 검증기(2.1) 통과분만. 의도 불일치는 V-7.
7. **고치기(F)** — 실패마다 원인을 **소스 조각 증거물**(파일·함수·코드 줄)에 묶어 설명하고, 빌더 도구별 지시로 만든다. 한 파일 앱은 고친 파일을 만들고 로컬로 띄워 실패했던 기준을 다시 돌려 통과할 때만 제공.
8. **재검사 고리(L)** — 같은 계획을 다시 실행해 기준별 전후를 비교. 모든 must 통과 또는 N회까지.

### 2.3 의도 입력 (기존 결정 그대로)
세 갈래(아이디어 / 주소 / 저장소·PRD) → "맞나요?"에서 **유저가 체크하거나 직접 적은 항목 = must**(2026-10-06 기본 체크 해제). 직접 적은 항목이 must로 인정되지 않는 의심 버그(파일럿 Claude 앱)는 v2 착수 전에 확인·수정.

## 3. 비용·청구 (V-6)
- 실측 기준: v1 런 $0.02~0.70. v2는 최상급 모델 전 구간 + 소스 읽기 + 재확인으로 **$2~5/런 [추정]**, 13앱 평가에서 [확정]으로 바꾼다.
- 런 시작 전에 예상 비용 범위를 보여 주고, 끝나면 원가·청구 예상액(원가 × 마진, 설정값)을 리포트·관리자 화면에 기록한다. 결제 연결은 과금 결정(D-23)과 별도 승인.
- 무료 공개 시의 상한·하루 예산 장치(#598)는 그대로 쓴다.

## 6. 위험
- 최상급 모델이 프로덕션 경로에서 닿지 않을 수 있다(Anthropic 차단) → S0에서 먼저 확정.
- 번들이 압축돼 읽기 어렵다 → 정적 사실은 가설용이고 판정은 실행 증거로 하므로 치명적이지 않다.
- 같은 앱도 실행마다 흔들린다 → G2부터 앱당 3회 평균.
- 로그인·결제 뒤는 기존 세 갈래 로그인(일회용 계정·시험 계정·직접 로그인 넘겨받기)으로, 캡차·문자 인증은 "확인 못 함".
