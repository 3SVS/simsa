# 증거 규칙 — 무엇을 "된다"고 말할 수 있는가

**제정 2026-08-25 (Bae 지시).** 이 규칙은 이 저장소에서 일하는 모든 세션·에이전트에
적용된다. 상태 보고·완료 선언·평가에 예외 없이 쓴다.

---

## 왜 생겼나

2026-08-20 평가에서 "코어 완성도 상급"이라고 보고했다. 근거는 **테스트 2000여 개
통과 · API 200 응답 · 머지·배포 완료**였다. 셋 다 참이었는데 제품은 망가져 있었다.

같은 주에 드러난 것:

| 무엇이 | 어떻게 안 보였나 |
|---|---|
| 스펙 생성이 **전 갈래에서 실패** | 폴백이 prefill을 못 다룸. 테스트는 전부 green |
| 의도 확인 카드가 **초안을 한 번도 못 줌** | API는 200. 응답 **내용**을 안 봤다 |
| #498이 **화면에서 무효** | 머지·배포 완료. 클라이언트 검증이 서버보다 엄격했다 |
| 진단 로그가 **두 글자에서 잘림** | 로그가 있다고 믿었다. 읽어보지 않았다 |
| 감사 장비가 **옛 화면을 잼** | 감사는 돌았고 P0=0이 나왔다 |

### 왜 구조적으로 눈이 멀었나

1. **코드를 평가하고 제품을 평가하지 않았다.** 테스트 통과는 부품이 명세대로
   동작한다는 뜻이지, 조립된 물건이 작동한다는 뜻이 아니다.
2. **200을 작동으로 셌다.** "200은 도달이지 쓸 만함이 아니다"를 교훈으로 적어놓고도
   벤더 프로브에만 적용하고 제품에는 적용하지 않았다.
3. **★정직성 설계가 고장을 감췄다.** 지어내지 않고 "가져오지 못했어요"라고 말하도록
   만들었더니, 망가진 기능이 **비명을 지르지 않고 공손하게 실패**했다. 날조하는
   시스템이었다면 이상한 결과가 나와 누군가 알아챘을 것이다.
   → **정직한 실패는 사용자에게는 옳지만, 우리에게는 침묵이다.** 그래서 정직하게
   실패하는 시스템일수록 **능동적 측정**이 더 필요하다.

## 규칙

### R1. 완료의 정의

> **"머지했다 · 배포했다 · 테스트 통과했다"는 완료가 아니다.**
> 완료는 **프로덕션에서 결과의 내용을 확인했을 때**만이다.

배포는 코드가 서버에 올라갔다는 사실이지, 사용자가 그 기능을 쓸 수 있다는 사실이
아니다. 둘 사이에 클라이언트 검증·설정·벤더·CORS·캐시가 있다.

### R2. 보고는 항상 세 칸으로

상태·평가·진행 보고는 반드시 아래로 나눈다. 뭉뜽그린 "상급/양호/완성" 같은 표현을
쓰지 않는다.

| 등급 | 뜻 | 무엇이 필요한가 |
|---|---|---|
| **라이브 확인** | 프로덕션에서 **내용**을 봤다 | 실브라우저 완주 또는 응답 본문 검사 |
| **테스트만 통과** | 부품은 명세대로 동작한다 | 단위·라우트 테스트 |
| **미측정** | 모른다 | — |

"미측정"을 부끄러워하지 않는다. **모르는 것을 안다고 말하는 것만이 결함이다.**

### R3. 상태 코드는 증거가 아니다

`200`은 "도달"이다. "쓸 만함"은 **응답 내용을 열어봐야** 안다. 판정 기준은 항상
**의존하는 성질 자체**여야 한다 — 스펙 생성이면 JSON이 파싱되고 항목이 들어 있는지,
검수면 판정이 붙었는지.

### R4. 측정 장비를 먼저 의심한다

제품을 바꾸면 **감사·프로브가 옛 화면을 재고 있지 않은지** 먼저 확인한다.
장비가 낡으면 green이 거짓말이 된다.

그리고 **읽히지 않는 계측은 없는 계측이다.** 로그를 넣었으면 실제로 읽어본다
(`console.warn`의 두 번째 인자가 wrangler tail에서 잘려 `head: {{` 두 글자만 보인
사례 — 그 탓에 가설을 두 번 틀렸다).

### R5. 같은 규칙이 양쪽에 있으면 테스트도 양쪽에서

입력 검증·정규화처럼 **클라이언트와 서버가 같은 규칙을 각자 갖는** 경우, 두 스위트가
**같은 입력 표**를 공유한다. 한쪽만 고치면 다른 쪽이 깨지게 만든다.
(클라이언트가 서버보다 엄격하면 기능이 통째로 무력화되는데 서버 테스트는 green이다.)

### R6. 두 번째 가설에서 멈춘다

같은 증상에 두 번째 가설을 세우게 되면 코드를 고치지 말고 **재는 도구를 먼저 만든다.**
403 하나에 다섯 번 틀렸고, 마지막엔 **재는 쪽을 바꿔**(노트북 vs Worker) 한 번에 갈렸다.

## 실행

- 완료 보고 때마다 R2의 세 칸 표를 쓴다.
- "라이브 확인" 칸에 넣을 때는 **무엇을 어떻게 봤는지** 한 줄로 적는다.
- 미측정 항목은 사라지지 않게 HANDOFF에 남긴다.
