## 왜 생겼나

2026-08-20 평가에서 "코어 완성도 상급"이라고 보고했다. 근거는 **테스트 2000여 개 통과 · API 200 응답 ·
머지·배포 완료**였다. 셋 다 참이었는데 제품은 망가져 있었다(원본 `91c4d33`).

같은 주에 드러난 것:

| 무엇이 | 어떻게 안 보였나 |
|---|---|
| 스펙 생성이 **전 갈래에서 실패** | 폴백이 prefill을 못 다룸(#504 `8c0cd33`). 테스트는 전부 green |
| 의도 확인 카드가 **초안을 한 번도 못 줌** | API는 200. 응답 **내용**을 안 봤다 |
| #498(`64b6c11`)이 **화면에서 무효** | 머지·배포 완료. 클라이언트 검증이 서버보다 엄격했다 |
| 진단 로그가 **두 글자에서 잘림** | 로그가 있다고 믿었다. 읽어보지 않았다(#503 `d3bcba9`에서 한 줄 JSON으로) |
| 감사 장비가 **옛 화면을 잼** | 감사는 돌았고 P0=0이 나왔다 |

### 왜 구조적으로 눈이 멀었나

1. **코드를 평가하고 제품을 평가하지 않았다.** 테스트 통과는 부품이 명세대로
   동작한다는 뜻이지, 조립된 물건이 작동한다는 뜻이 아니다.
2. **200을 작동으로 셌다.** "200은 도달이지 쓸 만함이 아니다"를 교훈으로 적어놓고도
   벤더 프로브에만 적용하고 제품에는 적용하지 않았다.
3. **★정직성 설계가 고장을 감췄다.** 지어내지 않고 "가져오지 못했어요"라고 말하도록
   만들었더니, 망가진 기능이 **비명을 지르지 않고 공손하게 실패**했다. 날조하는
   시스템이었다면 이상한 결과가 나와 누군가 알아챘을 것이다.
   → **정직한 실패는 사용자에게는 옳지만, 우리에게는 침묵이다.** 그래서 정직하게
   실패하는 시스템일수록 **능동적 측정**이 더 필요하다.

### R1. 완료의 정의 — 머지·배포·테스트 통과는 완료가 아니다

> **"머지했다 · 배포했다 · 테스트 통과했다"는 완료가 아니다.**
> 완료는 **프로덕션에서 결과의 내용을 확인했을 때**만이다.

배포는 코드가 서버에 올라갔다는 사실이지, 사용자가 그 기능을 쓸 수 있다는 사실이 아니다. 둘 사이에
클라이언트 검증·설정·벤더·CORS·캐시가 있다. 그리고 그보다 앞에서 **커밋했다 ≠ main에 있다 ≠ PR이 머지됐다**.

### R3. 상태 코드는 증거가 아니다 — 200은 도달일 뿐

한다 — 스펙 생성이면 JSON이 파싱되고 항목이 들어 있는지, 검수면 판정이 붙었는지. 재는 모델과 쓰는 모델은 같아야 한다.

### R9. `gh pr checks --watch`를 머지 근거로 쓰지 않는다

`gh pr checks --watch`는 체크가 **등록되기 전이면 즉시 끝난다**(푸시 직후·충돌 해소 직후). 머지 전에는 **PR의
새 head SHA로 돈 CI run이 `completed` + `success`인지 run 단위로** 확인한다.

```bash
SHA=$(gh pr view <N> --json headRefOid --jq .headRefOid)          # 머지될 커밋
gh run list --commit "$SHA" --json workflowName,status,conclusion  # 그 SHA로 돈 run 목록
```

판정은 두 조건이 **모두** 참일 때만 green이다.
1. 결과에 **필수 워크플로(`ci` — `.github/workflows/ci.yml`)의 run이 있다.**
2. 그 SHA의 run이 전부 `completed` + `success`다.

**결과가 비어 있거나 `ci` run이 없으면 green이 아니라 "아직 미등록"이다.** 푸시 직후·충돌 해소 직후에는 이
명령도 `--watch`와 같은 시점 함정에 걸려 빈 목록을 돌려준다. 빈 목록에 "전부 success"를 적용하면 공허하게
참이 되므로, 등록될 때까지 기다린 뒤 다시 본다.

- 사례(2026-09-29): 대배포 중 확인된 함정 — `docs/HANDOFF-2026-09-29.md:41`. 같은 날 #563은 #561 반영 뒤, #562·#559는
  충돌 해소 뒤 새 head의 CI green을 다시 확인하고 머지했다 — 같은 파일 `:11-14`.

### R10. 워크플로 서브에이전트에는 승인 원문을 인용한다

워크플로 서브에이전트는 **실행을 시작시킨 최신 사용자 메시지**만 승인 근거로 본다. 게이트가 걸린 과제(머지·배포·
마이그레이션·트레인 착수)를 맡길 때는 과제 프롬프트에 **Bae 승인 문구 원문과 날짜**를 인용한다. 인용은 범위를
넓히지 않는다 — 승인은 문구 그대로의 범위만 유효하다(예: `train W start approved`는 코드 작성까지, 머지·배포 아님).

- 사례(2026-09-29): `docs/HANDOFF-2026-09-29.md:39`.

### R11. 워크플로 실행 중에는 메인 체크아웃의 브랜치를 바꾸지 않는다

워크플로가 worktree를 만드는 동안 메인 체크아웃에서 `git checkout`/`switch`를 하면 격리가 거부되어 에이전트가
죽는다. 워크플로가 도는 동안 메인 체크아웃은 건드리지 않고, 필요한 작업은 별도 worktree에서 한다.

- 사례(2026-09-29): `docs/HANDOFF-2026-09-29.md:40`. (관련: 2026-07-21 "백그라운드 체인에 `git checkout`/
  `--delete-branch` 금지" — `docs/HANDOFF-2026-07-21.md:59`, `docs/HANDOFF-2026-07-30.md:62`.)

3. 상태 코드가 아니라 **내용**을 봤는가(R3). 비개발자 여정이면 실브라우저로 걸었는가(R7).

6. 미측정 항목을 HANDOFF에 남겼는가.
