## 만든 것

| 부분 | 내용 |
|---|---|
| 같은 계획 | 실행기가 `previousPlan`을 받으면 원 런의 가설·실험을 그대로 쓴다. 고친 뒤 정적 사실(예: localStorage)이 사라져도 원래 의심한 결함을 **같은 실험으로** 다시 확인해야 "해결"을 말할 수 있기 때문이다. 재사용은 증거물로 남긴다. 형식이 깨졌거나 기준이 다르면 새로 만든다 |
| 계획 보관 | v2 리포트에 `report.v2.plan`을 싣는다 |
| 엔진 물려받기 | 원 런이 v2면 재검사도 v2다. 조건: 스태프, 엔진 지정 없음, 로그인 요청 없음. Worker가 원 계획을 디스패치에 싣는다 |
| 비교 `src/v2-recheck.ts` | 아래 1 참고 |
| 저장 | 완료 콜백이 원 런 리포트와 비교해 `report.v2.comparison` · `report.v2.recheck {round, sourceCheckId}`에 싣는다. v1 재검사 비교(`agentComparison`)는 그대로 둔다 |

### 1. 비교(`src/v2-recheck.ts`)

- **기준별:**
  - 고쳐짐: fail·mismatch → pass.
  - 여전히: 계속 fail·mismatch.
  - 새로 깨짐: pass → fail·mismatch.
  - 확인 못 함으로 바뀜: fail → not_verified. **고쳐졌다고 세지 않는다.**
- **결함별(S5c 묶음 · S6 원인):**
  - 해결: 그 결함의 기준이 모두 통과.
  - 남음: 같은 원인으로 다시 실패.
  - 새 결함: 원 런에 없던 원인.
- **G4:** 지난번 검증을 통과한 고친 파일을 받은 기준이 지금 실제 앱에서 통과하는지 본다. 결과는 passNow / stillFailing / notVerified로 나눈다.
- **고리:** 회차는 원 런을 0으로 센다. 모든 must가 통과하거나 최대 3회차에 이르면 끝(`done`)이다.

테스트:
- 비교 5개.
- 실행기 계획 재사용 2개(수정 전 실패 확인).
- e2e 1개: v2 원 런 → "다시 확인" → v2 물려받음 + 원 계획 디스패치 → 완료 → 저장 리포트에 `newlyBroken`·`round 1`·`sourceCheckId`가 남는다. 실제 라우트와 SQLite로 돌린다.
- central-plane 전체 3503/3503.

## 아직 아닌 것

- **자동 고리**(고친 파일 → 재배포 → 재검사 자동 반복)는 빌드 파이프라인(Simsa 호스팅 앱)과 연결해야 한다. 이번 범위는 "사용자가 다시 확인을 누르면 같은 계획으로 비교"까지다.
- 대시보드에 비교·회차·G4 표시 — 화면 PR은 따로 낸다(화면·카피 위임 규칙).
- G4 실측(고친 파일을 실제로 반영한 비율)은 배포 뒤 실제 런에서만 잴 수 있다.
