# Simsa 검사 에이전트 — 스파이크 설계 (T0, 2026-10-05)

> 계기: 빌더 벤치마크 #1(docs/pilot-2026-10/bench1-results-2026-10-05.md)에서 사전 등록 진단 기준 3개 모두 미달. 원인 = 검사 엔진이 고정 규칙(visual-flow-plan.ts "결정론적 플래너": 첫 칸 "서울" → 버튼 하나 → 화면 변화)이라 **앱마다 의도를 읽고 검사 계획을 세워 실행하는 능력이 없다**. Bae 2026-10-05: 사용자는 의도 문장을 쓰지 않는다 — **자기 웹사이트 주소나 PRD만 올린다.**

## 가설 (1개)
사람이 짠 계획 없이, **주소(필수)와 선택 문서(PRD·기획서·빌더 프롬프트)만** 받은 AI 브라우저 에이전트가 앱의 의도를 스스로 파악해 검사 계획을 세우고 실행하면, 벤치마크 #1 사전 등록 기준을 넘는다.

## 입력 → 의도
| 입력 | 의도 획득 |
|---|---|
| 주소만(기본) | 에이전트가 앱을 둘러보고 "무엇을 하는 앱인가·핵심 흐름·완료 조건"을 추론 |
| 주소 + 문서 | 문서에서 완료 조건 추출 + 앱 추론과 합침. 문서와 앱의 차이는 그 자체로 "생각과 달라요" 근거 |
결과 맨 앞에 항상 "이 앱을 ○○로 이해하고 이렇게 검사했어요"(추론한 의도·조건 목록)를 보여 준다 — 오해를 사용자가 바로 본다.

## 구조 (4단계)
1. **이해**: 첫 화면 + 링크된 주요 화면(상한 N)을 열람 → 의도·핵심 흐름·완료 조건(must/should, 검증 방법 포함). 문서가 있으면 문서 우선.
2. **계획**: 조건마다 단계·한글 실데이터(예: 이름 "김민지", 010-1234-5678)·확인 방법. 조건이 저장·공유를 말하면 **새로고침 / 새 브라우저(다른 사용자) / 관리 화면** 확인을 계획에 넣는다.
3. **실행**: Playwright + LLM 관찰-행동 반복(접근성 트리·화면 텍스트·네트워크·콘솔 관찰 → 다음 행동 JSON: click/fill/select/press/goto/reload/new_session/back/done). 위험 조작(결제·실데이터 삭제·외부 발송) 차단 — 기존 classifyActionSafety 재사용, 자기가 만든 시험 데이터 취소만 예외.
4. **판정**: 조건별 통과/실패/확인 못 함 + 증거(화면·요청·콘솔). 최종 판정은 조건 결과로 결정. **실제 실패에서만** 고침 지시 생성.

## 실행 위치·비밀
검사 컨테이너(Playwright)에서 돌고, LLM은 **Worker 프록시**(빌드의 build-llm-proxy 방식: 잡 토큰·서버 키·서버 권위 예산)로만 부른다. 컨테이너에 키 없음. 사용량은 llm_usage에 기록.

## 스파이크 범위·안전
- 장비(staff) 티어에서만 켜지는 엔진 선택(`engine:"agent"`) — 실사용자 경로는 그대로.
- 상한 [PILOT]: 검사 1회 **$1 이하 · 10분 이하 · 행동 60회 이하**(넘으면 그 시점 결과로 "확인 못 함" 처리 + 기록).

## 판정 (실행 전 고정)
1. **벤치마크 #1 재측정**(정답지 그대로): 경로 ① 주소만(주 기준) ② 주소 + 빌더 프롬프트(문서). 통과 = 사전 등록 기준(반대 판정 0 · 앱별 일치 ≥4/6 · 고장 must 짚음 ≥50%) **그리고** 1회 비용·시간 상한 이내.
2. **일반화 확인**: 에이전트 코드 커밋을 고정한 **뒤** Bae가 정하는 새 주제로 벤치마크 #2(같은 사전 등록 절차). 같은 기준.
3. **수리**: 1·2 통과 시에만 고침 지시를 같은 빌더 대화에 붙여 넣어(≤2회) 재검사.
- 실패 시: 범위 축소("사용자가 가져온 오류·증상 진단 + 고침 지시") 제안 — 결정은 Bae.
- 보고는 숫자(통과/미달)로만. 중간 "거의 됨" 보고 금지.
