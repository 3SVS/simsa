## 1. 실행 전 준비 (한 번)

1. **승인 확인** — `pilot start approved.`와 범위((b)(c) 또는 (a))가 Bae 원문으로 있어야 한다. 없으면 멈춘다.
2. **정답지 선기록** — 템플릿을 복사해 **기대 칸만** 채우고(‘실행 후’ 표는 빈칸) 커밋한 뒤, **그 라운드의 첫 런 전에 main에 머지**한다(라운드별 정답지 PR 1개 — 저장소 규칙상 base=main PR). 이유: main은 스쿼시 머지라(예: `3a1ca07`·`9f02919`·`2956eb7` 모두 부모 1개, 커밋 시각 = 머지 시각) main 이력에 남는 정답지의 첫 커밋 시각은 **머지 시각**이고, 원 브랜치 커밋 SHA는 main 이력에 없다. `pilot-metrics`는 도구를 돌리는 체크아웃의 `git log --follow`로 선기록을 판정하므로, 머지가 첫 런보다 늦으면 main에서는 '아니오 (늦음)'이 나온다. 규칙:
   - **머지가 첫 런보다 늦어졌으면**: 정답지 브랜치를 지우지 않는다. 그 브랜치의 정답지 커밋 SHA·커밋 시각을 원가 시트 메모에 적고, 지표는 **그 브랜치를 체크아웃한 상태에서** 돌린다(브랜치 이력엔 원 커밋이 있다). 회고 §1에 "선기록 증거 = 브랜치 커밋 `<SHA>`"로 적는다.
   - 한 칸에 하나만 적는다. 예: 기대 판정 `안 돼요`. 선택지 나열(`작동해요 / 문제를 찾지 못했어요 / …`)을 그대로 두면 `pilot-metrics`가 **미선택**으로 본다.
   - 제목의 `(건 n/6)` 번호가 원가 시트 행과 정답지를 잇는 열쇠다. 1~3 = (b)(c), 4~6 = (a)로 둔다(권장).
   - 앱 주소는 Publish로 나온 주소 그대로(`…lovable.app` · `…vercel.app` · `…bolt.host`).
   - 이 런북도 같은 규칙이다: 이 PR이 main에 머지된 커밋이 첫 런보다 앞서야 §5가 사전 등록이다.
3. **한 브라우저** — 6건 모두 같은 브라우저(같은 userKey)에서 한다. 시크릿 창·다른 기기에서 만든 프로젝트는 다른 userKey에 묶여 지표 도구가 한 번에 못 읽는다(서버는 userKey 소유권으로만 프로젝트를 연다 — `apps/central-plane/src/routes/workspace.ts:466-486`).
4. **하루 한도** — 검수 10회·수리 5회 / userKey / UTC 하루 [PILOT] (`apps/central-plane/src/workspace/beta-limits.ts:66,68`).    - **4-a 경로**: 결과 화면의 「이 앱을 만든 도구로 고치기」 카드 → 「다시 확인」. 새 런이 원 런 id를 이어받아 만들어진다(sourceCheckId).

(선택)」 칸에 2단계에서 확정한 「이 앱이 하는 일」 한 줄을 **그대로** 넣고 → 「지금 검수하기」. ★이 버튼은 원 런 id를 보내지 않는다(`app/projects/[id]/visual-checks/page.tsx:190-195`) — 새 런에 sourceCheckId가 없어 **재검수로 세지지 않고 '후속 런'으로 따로 센다**(§4.4). 칸을 비워도 서버는 프로젝트에 저장된 확정 한 줄을 쓰지만(`apps/central-plane/src/routes/workspace-visual-check-runs.ts:409-422` — 적은 문장 › 원 런 › 프로젝트 확정 한 줄 › 기본 문장), 저장이 안 됐으면 기본 문장으로 떨어지므로 파일럿에서는 같은 한 줄을 넣어 자(尺)를 고정한다. 주소는 원 런을 모르므로 프로젝트의 가장 최근 앱 주소로 간다(같은 파일 `:459-463`) — 주소를 바꾸지 않았으면 같은 앱이다.
   - **4-c 경로**: 자동 재검수를 기다린다.
   - 어느 경로든 3단계처럼 결과를 확인한다.
6. **'이번 결과, 어떠셨어요?' 선택** — 마지막 런 결과 화면의 「이번 결과, 어떠셨어요?」에서 넷 중 하나를 고른다: 「생각대로 됐어요」(as_intended) · 「되긴 하는데 달라요」(works_but_different) · 「아직 안 돼요」(still_broken) · 「모르겠어요」(unsure).
   - **마지막 런의 답이 user_verdict 축과 규칙 R1의 입력이다.** 화면 판정을 보고 따라 답하지 않는다 — 앱을 직접 써 보고 답한다(따라 답하면 일치율이 무의미해진다).
   - 「아직 안 돼요」면 4~6을 다시 할 수 있다(재작업 +1). 건당 다시 확인은 **2회까지** [PILOT — 하루 3건 × (첫 확인 1 + 다시 확인 2) = 9 ≤ 한도 10(§1-4). 4-b의 「지금 검수하기」도 여기에 센다. 4-c 자동 재검수는 한도 밖이라 세지 않는다].
7. **수기 시트 기록** — `cost-sheet.md`의 이 건 줄에 support_minutes · 이의 · 재작업 · 개입 · 메모(§3).
8. **정답지 '실행 후' 칸** — 기대 칸은 건드리지 않고 실행 후 표만 채워 커밋한다:
   - 실제 판정 · 런 번호(`pilot-metrics` 가림 판 마크다운의 `런1`·`런2` — **런 id는 끝자리도 적지 않는다**: id가 ms 시각 + 무작위 4자라 끝자리와 시각이 함께 공개되면 복원된다, §7), 실제 user_verdict, 소요 시간, 6축 채움 n/6(§7 출력에서), 메모.
   - **실패 지점 일치 여부**: `예측 적중` / `다른 곳` / `실패 없음` 중 하나를 **사람이 판단해** 적는다. `pilot-metrics`는 예상 실패 지점과 기계 발견을 나란히 보여 줄 뿐 적중을 자동 판정하지 않는다.
9. **지표 뽑기** — §7.

## 4. 정의 (사전 등록 — `pilot-metrics`가 이대로 계산)

### 4.1 판정 매핑

기계 판정(서버 `decision`)을 정답지의 네 칸과 수용 쪽으로 옮기는 표. 판정 문구 출처: `apps/central-plane/src/nondev-report.ts:136-163`(DECISION_LABEL), 판정 규칙: 같은 파일 `decideFromEvidence`(385행~).

| decision | 화면 판정 문구 | 정답지 4칸 | 수용 쪽 |
|---|---|---|---|
| Ready | "정상 작동해요" | 작동해요 | accept |
| Conditionally Ready | "문제를 찾지 못했어요" | 문제를 찾지 못했어요 | accept |
| Needs Fix | "작동 안 해요 — 고쳐야 해요" | 안 돼요 | reject |
| 그 밖 전부 (Not Verified "확인 못 했어요" · User Acceptance Required "직접 눈으로 확인이 필요해요" · Needs Clarification · Needs Evidence · Needs Expert Review · Not Judged · Not Applicable · Do Not Build Yet · 모르는 값) | — | 사람 확인 필요 | abstain(보류) |

- 검수 실패(status = failed)는 판정이 아니라 실행 문제다 — 실패 런으로 따로 세고, L1의 "첫 런"은 **첫 끝난(done) 런**이다.
- 사람 라벨의 수용 쪽: as_intended → accept · still_broken → reject · **works_but_different → reject**(되긴 해도 의도와 다르면 수용이 아니다) · unsure → 라벨 아님.

### 4.2 6축 (건 단위 — 축마다 출처는 하나, 섞지 않는다)

| 축 | 출처 | 채움 조건 | 비는 대표 이유 |
|---|---|---|---|
| region | 프로젝트 `regionAtCreate` (GET /workspace/projects/:id, 0069) | 국가 코드가 있음 | 레거시 프로젝트 |
| built_with | 프로젝트 `builtWith` | 도구 1개 이상 또는 '기타' | 도구 선택 칸을 건너뜀 |
| topic | 프로젝트 `topicTags` (`src/workspace/topic-tags.ts` 결정론 키워드) | domain·pattern·ai_feature·integrations 중 하나라도 값이 있음. **빈 분류는 채움이 아니다** | 코드 갈래는 생성 때 아이디어가 비어 있다(`new/page.tsx:382-384` idea ""). 「네, 맞아요」로 한 줄이 저장되면 다시 분류된다 [미검증: 한국어 한 줄의 키워드 적중률] |
| finding_code | 끝난 런 **전부**의 발견 코드. D1 행을 넣으면 `finding_codes_json`, 아니면 API 리포트에서 서버 규칙대로(`src/routes/workspace-visual-check-runs.ts:297-308`) | 모든 끝난 런이 기록됨(`[]` = 측정했고 발견 0 — 채움) | 옛 컨테이너 이미지(코드 없는 발견) |
| user_verdict | **마지막 끝난 런**의 답 | 답이 있음 | 앞 런에만 답함 |
| resolved | 이 건 수리 잡의 `resolved` (0069) | 1 또는 0이 찍힘 | **붙여넣기 경로는 수리 잡이 없어 구조적으로 빈다** · 수리 PR 머지 신호가 없어 자동 재검수가 안 돎 · 자동 재검수가 돌았어도 판정이 Ready/Needs Fix가 아님(works=null — "문제를 찾지 못했어요" 포함, §2 4-c) · 재검수 진행 중·실패 |

- 건 채움 = 채운 축 / 6. 합계 = Σ 채운 축 / (6 × 건수).
- ★**붙여넣기 경로 건은 최대 5/6**(resolved). 규칙 R4의 문턱 5/6은 이 사실을 전제로 정했다.
- ★**resolved=1은 자동 재검수가 Ready("정상 작동해요" — 로그인 뒤 왕복 + 재로그인 뒤 데이터 유지 확인)일 때만**, 0은 Needs Fix일 때만 찍힌다. 수리 경로(4-c)라도 재검수가 "문제를 찾지 못했어요"면 resolved는 비고 그 건은 5/6이다. 도구는 비는 이유를 위 네 가지로 나눠 적는다.
- ★region은 **프로젝트 생성 시점** 값이다. 런 단위 region(`workspace_visual_checks.region`)은 API가 주지 않는다 — D1 행을 넣으면 참고 칸으로만 보인다.

### 4.3 기계 판정 vs 사람 라벨

- **L1**: 정답지 '기대 판정'(선기록) ↔ 첫 끝난 런의 4칸. 정확 일치와 쪽 관계 둘 다 낸다. 쪽 관계는 셋: **같은 쪽** · **반대 쪽**(accept ↔ reject) · **보류 차이**(한쪽만 '사람 확인 필요' = abstain).
- **L2**: 답이 있는 끝난 런마다 기계 쪽 ↔ 사람 쪽. 기계 보류(abstain)와 「모르겠어요」는 일치도 충돌도 아니다(따로 센다).
- ★**기계 보류는 L1·L2 모두 불일치가 아니다.** L1 보류 차이는 '보류 차이'로 따로 센다(R2 측정값에 함께 적힌다). 예: (b) 고장 앱에서 첫 런이 User Acceptance Required("직접 눈으로 확인이 필요해요" — 상호작용 뒤 스텝 실패 + 백엔드 실패 없음, `apps/central-plane/src/nondev-report.ts:404`)이고 기대가 `안 돼요`면 L1 보류 차이 — 불일치가 아니다. 판정을 내지 않은 것을 틀린 판정과 같이 세면 R2가 부푼다. 보류가 잦은 것은 R2가 아니라 회고 '예상 밖'에서 원문과 함께 다룬다.
- **건 불일치** = L1이 **반대 쪽**이거나 L2 충돌이 하나라도 있음. 잴 수 있는 신호(L1 같은/반대 쪽, L2 일치/충돌)가 하나도 없으면 '판정 불가'.
- 원문을 함께 남긴다: 런마다 decision · 화면 판정 문구 · 한 줄 요약 · 발견(코드 · severity · what 문장). 개수만 세지 않는다(2026-09-01 교훈).
- **예상 실패 지점 적중은 자동 판정하지 않는다** — 정답지 '실행 후 · 실패 지점 일치 여부'에 사람이 적은 값을 옮길 뿐이다.

### 4.4 시간·재검수

- **런별 생성→완료**: GET 상세 응답에는 완료 시각이 없다(`src/routes/workspace-visual-checks.ts:283-304` — createdAt만). D1 행의 `updated_at`(판정 저장은 updated_at을 건드리지 않는다 — `src/workspace/visual-check-db.ts:441-446`)을 넣을 때만 잰다. 없으면 '미측정'으로 표시한다.
- **건 단위**: 첫 런 생성 → 마지막 런 생성(고치는 시간 포함) · 첫 런 생성 → 마지막 끝난 런의 답 시각.
- **재검수** = sourceCheckId가 있는 런 수(결과 화면 「다시 확인」·「수리 확인 재검수」·자동 재검수).
- **후속 런** = 첫 끝난 런보다 뒤에 만든 런 중 sourceCheckId가 **없는** 런 수. §2 5단계의 4-b 경로(목록 화면 「지금 검수하기」)는 계보를 남기지 않아 재검수로 세지지 않는다 — 그래서 따로 센다. 첫 끝난 런 **전**의 재시도(실패 런 뒤 다시 걸기)는 어느 쪽도 아니다.

공통 규칙:
- **문턱 확정 2026-10-04 (Bae "남은 결정 다 너의 제안대로")**: R1 0→≤1 · R2 정반대 1건·보류 차이 ≥2/3 추가 · R5 0→≤1. 첫 런 전 main 머지 = 사전 등록. 이후 변경은 정정 기록으로만.
- **입력 부족**(답 없음 · 시트 미기입 · (a) 전)이면 판정하지 않는다. 채운 뒤 다시 뽑는다. 끝내 못 채우면 그 사실을 회고에 적는다.
- **문턱을 넘어도 자동으로 무엇을 시작하지 않는다.** 회고에서 제안하고, 착수는 Bae의 승인 문구(`train N start approved` 등)로만 한다.
- n = 3·6은 비율 추정이 아니다(계획 §2.7: "6/6 성공도 Wilson 하한 61%"). 규칙은 **멈추고 다시 볼 신호**이지 통계적 결론이 아니다.
- 계획 §2.7 ⑥의 "결제 화면 진입 < 10% → 유입 문제" 같은 가격 퍼널 규칙은 과금 경로(Train $)가 샌드박스 전이라 이번 5개에서 뺐다.

## 6. 회고 양식 (3라운드)

## 7. `pilot-metrics` 쓰는 법

**userKey** — 파일럿 브라우저의 개발자 도구 콘솔에서 `localStorage.getItem("conclave_user_key")`(`apps/dashboard/src/lib/workflow-store.ts:225`). 저장소 **밖** 파일(예: `~/simsa-pilot-userkey.txt`)이나 환경변수에만 둔다. 커밋·채팅 붙여넣기 금지. 도구는 userKey를 출력·로그·오류 문구에 넣지 않는다 — 수집은 필요한 칸만 옮기는 화이트리스트다. 그래도 출력 원문(JSON·마크다운)에 userKey가 들어 있으면 **가리지 않고 멈춘다**: 파일을 쓰지 않고, 새는 칸의 경로(예: `cases[0].title`)만 알린다(값은 알리지 않는다). 멈췄다면 화이트리스트 회귀이므로 그 칸을 고친 뒤 다시 돌린다 — 가려서 쓰고 넘어가지 않는다.

**기본 실행** (저장소 루트, Git Bash):

```bash
export SIMSA_USER_KEY="$(cat ~/simsa-pilot-userkey.txt)"
node tools/simsa-completion-loop-spike/pilot-metrics.mjs \
  --case proj_xxxxxxxx=docs/pilot-2026-10/answer-key-01-예약앱.md \
  --case proj_yyyyyyyy=docs/pilot-2026-10/answer-key-02-가계부.md \
  --case proj_zzzzzzzz=docs/pilot-2026-10/answer-key-03-동아리출석.md \
  --sheet docs/pilot-2026-10/cost-sheet.md
```

프로젝트 id는 대시보드 주소창의 `/projects/proj_…` 부분이다. 출력은 `tools/simsa-completion-loop-spike/pilot-metrics-out/`(gitignore)에 JSON과 마크다운으로 남는다.

**선택 입력**
- 런별 생성→완료 시간: `--print-d1-sql`(같은 `--case`들과 함께)로 읽기 전용 질의를 받아 로컬 wrangler로 실행 → `--d1-rows <파일>`. 예: `pnpm --filter @simsa/central-plane exec wrangler d1 execute conclave-ai --remote --json --command "<질의>" > ~/pilot-d1-rows.json`. [미검증: 노트북 wrangler의 D1 읽기 권한 상태] 질의는 내용·식별 컬럼(user_key·intent·report_json·target_url)을 고르지 않는다.
- 서비스 전체 채움(파일럿 한정 아님): GitHub Actions → `ops-probe` → target `d1-readonly`, query `envelope-fill-rate`(또는 `repair-fill-rate`) → job summary의 표를 파일로 저장 → `--ops-fill <파일>`.
- 재계산: `--snapshot-in <이전 JSON>` — 네트워크 없이, 정답지·시트만 다시 읽는다(실행 후 칸을 채운 뒤 표를 다시 뽑을 때).
- `--no-mask`: 마크다운에서도 id·초 단위 시각·국가 값을 가리지 않는다(로컬 확인용 — 공개 저장소에 붙이지 않는다).

**공개 저장소 주의** — 3SVS/simsa는 공개 저장소다(`apps/central-plane/scripts/d1-readonly-queries.mjs` 머리 주석).
- **JSON은 올리지 않는다** — 전체 런 id·프로젝트 id·앱 주소·초 단위 시각이 있다.
- **마크다운(기본 가림 판)**: 런 id 대신 건 안 순번(`런1` = 그 건의 첫 런, `런2 ⟵ 런1` = 런1을 이은 재검수), 시각은 분 단위 UTC, region은 '✓ 기록됨'으로만 낸다. 런 id는 `wvc_` + ms 시각(base36 끝 6자) + 무작위 4자라(`apps/central-plane/src/workspace/visual-check-db.ts:97-101`) 예전처럼 끝 4자리를 남기고 ms 생성 시각을 함께 내면 id 전체가 복원된다 — 그래서 id 조각을 하나도 내지 않는다(분 단위 시각만으로는 복원할 수 없다).
- ★**d1-readonly 공개 출력 규칙과의 차이** — `d1-readonly-queries.mjs:15-19`(PR #561 검증)은 공개 출력에서 id·초 단위 시각·국가 값·사람 판정 값·수리 해결 여부 값을 뺀다(이용자가 적을 때 그것만으로 사람을 가리킬 수 있어서). 가림 판도 id·초 단위 시각·국가 값은 뺀다. 그러나 **판정·user_verdict·resolved 값은 남긴다** — 파일럿 결과 그 자체이기 때문이다. 이 차이는 **파일럿 데이터가 운영자 본인(Bae)의 프로젝트와 본인 판정뿐**이라는 전제에서만 성립한다. 실유저 프로젝트가 한 건이라도 섞이면 가림 판도 `RESULT.md`에 붙이지 않는다. 공개 저장소에 판정 값을 싣는 것 자체를 원치 않으면 `RESULT.md`에는 규칙 표(pilot-metrics 마크다운 §1)와 건수만 싣고 나머지는 저장소 밖에 둔다 — 이 선택은 Bae가 라운드 1 회고 전에 정한다.

**부작용 1건** — 끝난 런의 상세 GET은 서버에 '리포트 열람' 사용 이벤트(`workspace_report_viewed`)를 1건씩 남긴다(`apps/central-plane/src/routes/workspace-visual-checks.ts:271-281`). 퍼널 분석에서는 파일럿 userKey를 뺀다. 그 밖에는 읽기 전용이다 — 검수·수리를 시작하지 않는다.

## 8. 알려진 한계 (실행 전에 적어 둔다)

- 붙여넣기 경로는 resolved가 구조적으로 비어 6축 최대 5/6이다(§4.2). 손으로 누른 「수리 확인 재검수」도 resolved를 찍지 않는다(§2 4-c).
- 수리 경로(4-c)라도 resolved=1은 자동 재검수가 Ready(로그인 뒤 왕복 확인)일 때만이다 — 재검수가 "문제를 찾지 못했어요"면 works=null이라 resolved는 빈다(§2 4-c, §4.2).
- '고칠 것 없음' 결과(4-b)에서 다시 확인하면 계보(sourceCheckId)가 남지 않는다 — 결과 화면에 「다시 확인」이 없어 목록 화면 「지금 검수하기」로 걸기 때문이다(§2-5). 이런 런은 재검수가 아니라 '후속 런'으로 센다(§4.4). 제품 쪽 해결(‘문제 못 찾음’ 결과 화면에도 계보를 잇는 「다시 확인」)은 파일럿 범위 밖 — 라운드 1 회고의 '다음 행동' 후보로 적는다.
- 런별 완료 시각은 API에 없다 — D1 행 입력이 없으면 '미측정'(§4.4).
- region은 프로젝트 생성 시점 값이다(§4.2).
- topic은 한국어 한 줄에서 키워드가 얼마나 잡히는지 [미검증].
- (a) 빌드 지표(빌드 결과·spent_usd)는 수기다 — 빌드 실행체가 아직 없다(계획 §5.1 186행: kind=build → builder_stage_not_implemented).
- 지표 도구 테스트(화면 문구 드리프트 가드 포함)는 CI에 걸려 있지 않다(`tools/`는 pnpm 워크스페이스 밖 — `pnpm-workspace.yaml`). 그래서 대시보드 문구가 바뀌어도 PR이 빨개지지 않는다 — §1-6처럼 사람이 돌린다. 로컬에서 `node --test tools/simsa-completion-loop-spike/test/pilot-metrics.test.mjs`.
