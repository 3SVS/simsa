## 3. 원가 수기 시트

[`cost-sheet.md`](cost-sheet.md)에 건마다 한 줄. 이 시트가 BM 원가표의 [추정] '지원 시간'을 실측으로 바꾸는 입력이다(계획 §2.6 민감도 표 124행: "지원 시간 … 저가 SKU 지배 변수. 파일럿 support_minutes 수기 시트로 교체").

| 칸 | 적는 법 | 넣는 것 / 빼는 것 |
|---|---|---|
| support_minutes | 분, 숫자만(`12` 또는 `12분`) | **넣는다**: 버튼·주소 찾기, 오류 문구 해석, 지시를 다시 쓰거나 설명한 시간, 도구 사용법 확인. **뺀다**: 검수 대기(1~4분), 빌더가 고치는 동안의 대기, 정답지 작성 |
| 이의(생각과 다름) | `예 — 한 줄` / `아니오` | 과정 중 결과 판정이나 고침이 "내 생각과 다르다"고 느낀 적이 있으면 예. 마지막 답이 「되긴 하는데 달라요」가 아니어도 과정 중 이의는 적는다 |
| 재작업 | 횟수 | 첫 고침 뒤 **추가로** 한 고침 → 다시 확인 왕복 수. 한 번에 됐으면 0 |
| 개입(직접 쓴 지시) | `예` / `아니오` | Simsa가 준 지시 대신 사람이 쓰거나 고친 지시를 빌더에 넣었으면 예 |
| spent_usd | 달러, 숫자만 | (a)만. 빌드 원가 — 사용량 원장(L-3)이 라이브되기 전에는 수기 |
| 빌드 결과 | `성공` / `실패` | (a)만. 계획 §5.5 D-23(제안) ②의 성공 정의 기준 |

## 4. 정의 (사전 등록 — `pilot-metrics`가 이대로 계산)

### 4.1 판정 매핑

기계 판정(서버 `decision`)을 정답지의 네 칸과 수용 쪽으로 옮기는 표. 판정 문구 출처: `apps/central-plane/src/nondev-report.ts:136-163`(DECISION_LABEL), 판정 규칙: 같은 파일 `decideFromEvidence`(385행~).

| decision | 화면 판정 문구 | 정답지 4칸 | 수용 쪽 |
|---|---|---|---|
| Ready | "정상 작동해요" | 작동해요 | accept |
| Conditionally Ready | "문제를 찾지 못했어요" | 문제를 찾지 못했어요 | accept |
| Needs Fix | "작동 안 해요 — 고쳐야 해요" | 안 돼요 | reject |
| 그 밖 전부 (Not Verified "확인 못 했어요" · User Acceptance Required "직접 눈으로 확인이 필요해요" · Needs Clarification · Needs Evidence · Needs Expert Review · Not Judged · Not Applicable · Do Not Build Yet · 모르는 값) | — | 사람 확인 필요 | abstain(보류) |

- 검수 실패(status = failed)는 판정이 아니라 실행 문제다 — 실패 런으로 따로 세고, L1의 "첫 런"은 **첫 끝난(done) 런**이다.
- 사람 라벨의 수용 쪽: as_intended → accept · still_broken → reject · **works_but_different → reject**(되긴 해도 의도와 다르면 수용이 아니다) · unsure → 라벨 아님.

### 4.2 6축 (건 단위 — 축마다 출처는 하나, 섞지 않는다)

| 축 | 출처 | 채움 조건 | 비는 대표 이유 |

| region | 프로젝트 `regionAtCreate` (GET /workspace/projects/:id, 0069) | 국가 코드가 있음 | 레거시 프로젝트 |
| built_with | 프로젝트 `builtWith` | 도구 1개 이상 또는 '기타' | 도구 선택 칸을 건너뜀 |
| topic | 프로젝트 `topicTags` (`src/workspace/topic-tags.ts` 결정론 키워드) | domain·pattern·ai_feature·integrations 중 하나라도 값이 있음. **빈 분류는 채움이 아니다** | 코드 갈래는 생성 때 아이디어가 비어 있다(`new/page.tsx:382-384` idea ""). 「네, 맞아요」로 한 줄이 저장되면 다시 분류된다 [미검증: 한국어 한 줄의 키워드 적중률] |
| finding_code | 끝난 런 **전부**의 발견 코드. D1 행을 넣으면 `finding_codes_json`, 아니면 API 리포트에서 서버 규칙대로(`src/routes/workspace-visual-check-runs.ts:297-308`) | 모든 끝난 런이 기록됨(`[]` = 측정했고 발견 0 — 채움) | 옛 컨테이너 이미지(코드 없는 발견) |
| user_verdict | **마지막 끝난 런**의 답 | 답이 있음 | 앞 런에만 답함 |
| resolved | 이 건 수리 잡의 `resolved` (0069) | 1 또는 0이 찍힘 | **붙여넣기 경로는 수리 잡이 없어 구조적으로 빈다** · 수리 PR 머지 신호 없음(§2 4-c) |

- 건 채움 = 채운 축 / 6. 합계 = Σ 채운 축 / (6 × 건수).
- ★**붙여넣기 경로 건은 최대 5/6**(resolved). 규칙 R4의 문턱 5/6은 이 사실을 전제로 정했다.
- ★region은 **프로젝트 생성 시점** 값이다. 런 단위 region(`workspace_visual_checks.region`)은 API가 주지 않는다 — D1 행을 넣으면 참고 칸으로만 보인다.

### 4.3 기계 판정 vs 사람 라벨

- **L1**: 정답지 '기대 판정'(선기록) ↔ 첫 끝난 런의 4칸. 정확 일치와 같은 쪽(수용 쪽) 둘 다 낸다.
- **L2**: 답이 있는 끝난 런마다 기계 쪽 ↔ 사람 쪽. 기계 보류(abstain)와 「모르겠어요」는 일치도 충돌도 아니다(따로 센다).
- **건 불일치** = L1이 다른 쪽이거나 L2 충돌이 하나라도 있음. 둘 다 잴 수 없으면 '판정 불가'.
- 원문을 함께 남긴다: 런마다 decision · 화면 판정 문구 · 한 줄 요약 · 발견(코드 · severity · what 문장). 개수만 세지 않는다(2026-09-01 교훈).
- **예상 실패 지점 적중은 자동 판정하지 않는다** — 정답지 '실행 후 · 실패 지점 일치 여부'에 사람이 적은 값을 옮길 뿐이다.

### 4.4 시간·재검수

- **런별 생성→완료**: GET 상세 응답에는 완료 시각이 없다(`src/routes/workspace-visual-checks.ts:283-304` — createdAt만). D1 행의 `updated_at`(판정 저장은 updated_at을 건드리지 않는다 — `src/workspace/visual-check-db.ts:441-446`)을 넣을 때만 잰다. 없으면 '미측정'으로 표시한다.
- **건 단위**: 첫 런 생성 → 마지막 런 생성(고치는 시간 포함) · 첫 런 생성 → 마지막 끝난 런의 답 시각.
- **재검수** = sourceCheckId가 있는 런 수.

## 7. `pilot-metrics` 쓰는 법

**userKey** — 파일럿 브라우저의 개발자 도구 콘솔에서 `localStorage.getItem("conclave_user_key")`(`apps/dashboard/src/lib/workflow-store.ts:225`). 저장소 **밖** 파일(예: `~/simsa-pilot-userkey.txt`)이나 환경변수에만 둔다. 커밋·채팅 붙여넣기 금지. 도구는 userKey를 출력·로그·오류 문구에 넣지 않고, 쓰기 직전에 한 번 더 검사해 들어 있으면 파일을 쓰지 않고 멈춘다.

**기본 실행** (저장소 루트, Git Bash):

```bash
export SIMSA_USER_KEY="$(cat ~/simsa-pilot-userkey.txt)"
node tools/simsa-completion-loop-spike/pilot-metrics.mjs \
  --case proj_xxxxxxxx=docs/pilot-2026-10/answer-key-01-예약앱.md \
  --case proj_yyyyyyyy=docs/pilot-2026-10/answer-key-02-가계부.md \
  --case proj_zzzzzzzz=docs/pilot-2026-10/answer-key-03-동아리출석.md \
  --sheet docs/pilot-2026-10/cost-sheet.md
```

프로젝트 id는 대시보드 주소창의 `/projects/proj_…` 부분이다. 출력은 `tools/simsa-completion-loop-spike/pilot-metrics-out/`(gitignore)에 JSON과 마크다운으로 남는다.

**선택 입력**
- 런별 생성→완료 시간: `--print-d1-sql`(같은 `--case`들과 함께)로 읽기 전용 질의를 받아 로컬 wrangler로 실행 → `--d1-rows <파일>`. 예: `pnpm --filter @simsa/central-plane exec wrangler d1 execute conclave-ai --remote --json --command "<질의>" > ~/pilot-d1-rows.json`. [미검증: 노트북 wrangler의 D1 읽기 권한 상태] 질의는 내용·식별 컬럼(user_key·intent·report_json·target_url)을 고르지 않는다.
- 서비스 전체 채움(파일럿 한정 아님): GitHub Actions → `ops-probe` → target `d1-readonly`, query `envelope-fill-rate`(또는 `repair-fill-rate`) → job summary의 표를 파일로 저장 → `--ops-fill <파일>`.
- 재계산: `--snapshot-in <이전 JSON>` — 네트워크 없이, 정답지·시트만 다시 읽는다(실행 후 칸을 채운 뒤 표를 다시 뽑을 때).
- `--no-mask`: 마크다운에서도 id를 가리지 않는다(로컬 확인용).

**공개 저장소 주의** — 3SVS/simsa는 공개 저장소다(`apps/central-plane/scripts/d1-readonly-queries.mjs` 머리 주석). JSON에는 전체 id·앱 주소가 있으므로 올리지 않는다. 마크다운은 id를 끝 4자리만 남기므로 `RESULT.md`에 붙여도 된다.

**부작용 1건** — 끝난 런의 상세 GET은 서버에 '리포트 열람' 사용 이벤트(`workspace_report_viewed`)를 1건씩 남긴다(`apps/central-plane/src/routes/workspace-visual-checks.ts:271-281`). 퍼널 분석에서는 파일럿 userKey를 뺀다. 그 밖에는 읽기 전용이다 — 검수·수리를 시작하지 않는다.

## 8. 알려진 한계 (실행 전에 적어 둔다)

- 붙여넣기 경로는 resolved가 구조적으로 비어 6축 최대 5/6이다(§4.2). 손으로 누른 「수리 확인 재검수」도 resolved를 찍지 않는다(§2 4-c).
- 런별 완료 시각은 API에 없다 — D1 행 입력이 없으면 '미측정'(§4.4).
- region은 프로젝트 생성 시점 값이다(§4.2).
- topic은 한국어 한 줄에서 키워드가 얼마나 잡히는지 [미검증].
- (a) 빌드 지표(빌드 결과·spent_usd)는 수기다 — 빌드 실행체가 아직 없다(계획 §5.1 186행: kind=build → builder_stage_not_implemented).
- 지표 도구 테스트는 CI에 걸려 있지 않다(`tools/`는 pnpm 워크스페이스 밖 — `pnpm-workspace.yaml`). 로컬에서 `node --test tools/simsa-completion-loop-spike/test/pilot-metrics.test.mjs`.
- #564 배포 여부 [미확인](§1-5).
