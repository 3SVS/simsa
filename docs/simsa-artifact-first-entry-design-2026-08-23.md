**티어:** T2-P (자기주도 제품 — 결정 잠금 + 게이트) · **스코프:** 작게(Bae 확정 2026-08-23)

## 0. 왜 지금 이걸 바꾸나

Bae 지적: *"앱을 만들어서 검수를 받아보고 싶은 사람도 제품설명·깃헙 연결·url 연결·
데이터베이스 연결을 다 지나가야 해? 앱주소나 깃헙리포를 올려서 그걸 검수 먼저 받고,
그 후에 고칠 점이 있으면 그걸 설명하면서 빌더팩으로 다시 줘야 하는 거 아닐까"*

### 실측한 현재 상태 (기억 아님, 코드 확인)

- 코드 갈래 첫 화면의 **하드 게이트는 앱 이름 하나뿐**이다. 빌더칩·호스팅·데이터·
  설명·"꼭 작동해야 하는 것" 5개는 전부 선택이며 빈칸으로 넘어간다.
- GitHub도 필수가 아니다 — `inspectionEmptyStateDoor`는 `hasDeployUrl`이면 곧장
  `"run"`을 준다.
- "데이터베이스 연결"은 연결이 아니라 **질문**("어디에 저장하나요")이고, 빌더팩을
  그 스택에 맞추려는 정보다.

### 그럼에도 지적이 맞는 이유

**정작 사용자가 손에 들고 온 것(앱 주소·리포)을 첫 화면에서 묻지 않는다.** URL 입력칸은
두 화면 뒤(`/sources`)에 있고, 첫 화면은 이름 + 선택 5종으로 채워져 있다.
**필수가 아니어도 보이는 순서가 요구로 읽힌다.**

그리고 더 큰 낭비: **우리가 묻는 것 대부분은 제출물에서 알아낼 수 있다.** 리포의
`package.json`·`vercel.json`·Supabase 설정에서 빌더·호스팅·데이터가 읽히고, URL의 응답
헤더·번들에서 호스팅이 나온다. **감지할 수 있는 것을 인터뷰로 묻고 있다.**

### 이미 있는 것 — 새로 만드는 게 아니다

검수결과 → 고쳐보기(`/fixes`) → 빌더팩(`/export`) 경로는 **이미 라이브다**.
아이디어→스펙 생성기도, 문서→스펙 변환(`workspace-document-intake`)도 있다.
이 작업은 **앞단의 순서를 뒤집고, 기존 기계의 입력 어댑터를 하나 추가하는 일**이다.

## 1. Bae가 제기한 두 반론 — 설계의 중심

> *"앱주소만 주면 그걸로 로그인 못해서 QA도 못 돌릴 거 아냐. 제작 의도도 모르고."*

둘 다 맞다. 그리고 **첫 번째는 지금도 이미 사실이다.**

### 반론 A — 로그인 벽 (기존 한계, 신규 아님)

검수 러너(`visual-flow-plan.ts`)에는 **로그인 기능이 아예 없다.** 랜딩에서 안전한 CTA를
점수로 골라 눌러보는 결정론적 플로우이고, 자격증명을 받는 경로도 세션을 유지하는 경로도
없다. 즉 **오늘도 로그인 뒤는 못 본다.** 제출물-우선 진입이 이 한계를 만드는 게 아니라,
URL이 정문이 되면서 **이 한계가 정면에 드러난다.**

→ 이 설계는 한계를 **없애는 척하지 않고, 정직하게 말하고 깊이를 단계로 판다.**

### 반론 B — 제작 의도를 모른다

맞다. 다만 *"모른다"가 "물어봐야 한다"를 뜻하지는 않는다.* 우리에겐 이미 자유 텍스트에서
스펙을 뽑는 생성기가 있다. 방향만 바꾸면 **제출물 → 의도 초안**이 된다. 비개발자에게
빈칸을 주는 것보다 **초안을 주고 고치게 하는 편이 훨씬 쉽다** — 이건 이 제품의 기존
원칙(추천 답안·선택 단계)과도 일치한다.

## 2. 결정 (D-번호)

### D-1 [LOCKED] 첫 화면은 제출물 한 칸이다

새 프로젝트의 코드 갈래 첫 화면은 **"앱 주소 또는 GitHub 리포"** 입력 하나로 시작한다.
이름·빌더·호스팅·데이터·설명·필수동작은 **이 화면에서 제거**한다(삭제가 아니라 **이동**).

- 받는 형식: `https://…` URL, `owner/repo`, GitHub URL(정규화해서 `owner/repo`로).
- **zip/패키지는 이번 스코프에서 제외**한다(D-6 참조).

### D-2 [LOCKED] 제출 즉시 1차 검수를 돌린다 — 가치를 먼저 보여준다

제출물을 받으면 **아무것도 더 묻지 않고** 곧장 1차 검수를 시작한다. 1차 검수의 목표는
완결성이 아니라 **"이 앱이 실제로 서 있는가"** 다: 페이지가 뜨는가, 콘솔/네트워크가
터지는가, 눈에 보이는 주요 동작이 반응하는가(겉만 번지르르한 앱 탐지).

- 항목 기반 정밀 판정은 여기서 하지 않는다 — 기준이 아직 없기 때문이다(정직).
- 결과 카드에 **"로그인 뒤는 보지 못했습니다"** 를 항상 명시한다(D-4).

### D-3 [LOCKED] 의도·스택은 묻지 않고 **추론한 뒤 확인받는다**

1차 검수와 **병렬로** 제출물에서 초안을 뽑는다.

| 출처 | 뽑는 것 |
|---|---|
| 리포: `README`, `package.json`, 라우트/폴더 구조 | 제품 의도 초안 · 빌더 · 호스팅 · 데이터 |
| URL: 랜딩 텍스트, 응답 헤더, 번들 힌트 | 제품 의도 초안 · 호스팅 |

결과 화면에서 **"이 앱은 ~로 보입니다. 맞나요?"** 로 제시하고 사용자가 고친다.
확정된 의도로 **체크리스트 항목**을 만들고, 그때부터 정밀 검수가 가능해진다.

- **추론 실패는 정직하게 비운다.** 지어낸 의도는 잘못된 기준을 만들고, 잘못된 기준은
  잘못된 검수 결과를 만든다 — 이 제품에서 가장 비싼 실패다.
- 추론에 쓰는 LLM 경로는 기존 `anthropicMessages`(벤더 폴백 적용)를 탄다.

### D-4 [LOCKED] 깊이는 단계로 판다 — 못 본 것을 반드시 말한다

검수 깊이를 3단으로 명시하고, 결과 화면이 **지금 몇 단인지와 다음 단으로 가는 법**을
항상 보여준다.

| 단계 | 필요한 것 | 볼 수 있는 것 |
|---|---|---|
| **L1 공개 표면** | URL 하나 | 페이지 로드·에러·공개 화면의 주요 동작 |
| **L2 코드 열람** | + GitHub 리포 | 로그인 뒤 로직·설정·의존성(정적 판독) |
| **L3 로그인 통과** | + 테스트 계정 | 로그인 뒤 화면의 실제 동작 |

**L3는 이번 스코프에서 구현하지 않는다.** 다만 결과 화면에 *"로그인 뒤는 보지
못했습니다"* 를 **반드시** 표기해, 사용자가 L1 결과를 전체 검수로 오해하지 않게 한다.
이 표기는 선택이 아니라 **정직성 요건**이다.

### D-8 [LOCKED] 연결 시점에 도달성을 재고, **막지 않고 알려준다**

Bae 지시(2026-08-23): *"연결 시점부터 확인하는 방향으로 고쳐줘. 로그인 기능이 없으면
그냥 리포 주소나 앱 주소만 넣어도 돌아가도록 유연하게 적용해줘."*

제출물을 받는 즉시 지금 어디까지 보이는지 재고, **그 자리에서** 말한다. 종전엔 조용히
저장해 놓고 한참 뒤 자동수리 단계에서 *"GitHub 계정 연결이 필요해요"* 로 막았다.

**이 계측은 게이트가 아니다.** 어떤 결과가 나와도 소스는 저장된다 — 우리 판단이 틀릴 수
있고(레이트리밋·일시적 장애), 사용자를 자기 저장소로부터 막을 권한이 우리에게 없다.

세 상태를 **반드시 구분**한다:

| 상태 | 뜻 | 화면 |
|---|---|---|
| `readable` | 지금 이대로 읽힌다(공개, 또는 내 토큰으로 보이는 비공개) | 된다고 말한다. 설치 링크 없음(노이즈) |
| `needs_access` | 우리 눈엔 안 보인다 | **비공개일 수도, 주소 오타일 수도** — 두 갈래를 다 열어 둔 문구 + App 설치 경로 |
| `unknown` | 재지 못했다(레이트리밋·네트워크·타임아웃) | "저장했고 검수할 때 다시 시도" — **"안 된다"고 말하지 않는다** |

`unknown`을 `needs_access`로 뭉뜽그리면 레이트리밋에 걸린 순간 멀쩡한 공개 저장소가
"비공개인가 봐요"로 오진된다. 비인증 GitHub API는 IP당 60회/시간이고 Worker는 egress IP를
공유하므로 이 오진은 드물지 않다.

**인증 정책:** 사용자의 GitHub 연결이 있으면 그 토큰으로(비공개도 보이고 한도도 넉넉),
없으면 **비인증으로** 잰다 — 공개 저장소를 읽는 데 계정이 필요 없다는 사실을 그대로 쓴다.

**앱 주소:** 401/403/500도 `readable`로 본다. 서버가 살아 있다는 증거이고, 로그인이
필요하거나 앱이 고장 났다는 것은 **검수가 할 말**이지 연결 실패가 아니다.

### D-9 [LOCKED] 다계정 사용자에겐 App 설치가 정답이다

Bae 실사용: *"깃헙 계정이 많아서 연결이 잘 안 되더라."* 원인은 **OAuth**다 — GitHub OAuth는
기존 승인을 조용히 재사용해서, 계정을 바꾸려면 Simsa 연결 해제 → github.com 계정 전환 →
재연결의 3단계를 매번 밟아야 한다.

**GitHub App 설치는 설치 화면에서 계정/조직을 고르게 하고 저장소도 선택할 수 있다.**
그래서 `needs_access`일 때 App 설치 경로를 **그 자리에서** 제시한다(D-8). 설치 안내를
실패 후의 구제책이 아니라 **동등한 선택지**로 올리는 것은 별도 스테이지(AF-7)로 둔다.

### D-10 [LOCKED] 클라이언트 검증은 서버보다 엄격할 수 없다

2026-08-23 실제 사고: 서버(#498)가 GitHub 주소를 받도록 고쳐졌는데 대시보드의
`validateSourceInput`이 여전히 `owner/repo`만 통과시켜 **UI에서는 아무것도 달라지지
않았다.** 서버 테스트는 전부 green이라 사고가 드러나지 않았다.

→ 입력 형식 규칙이 양쪽에 있는 경우, **두 스위트가 같은 입력 표를 공유**한다
(`central-plane/test/github-repo-ref.test.mjs` ↔ `dashboard/test/source-connect-reachability.test.mjs`).
한쪽만 고치면 다른 쪽이 깨진다.

### D-5 [OPEN] 테스트 계정(L3)을 받을 것인가

**재검토 트리거:** L1+L2 진입이 라이브로 돌아간 뒤, "로그인 뒤를 못 본다"가 실제 사용자
불만·이탈로 관측될 때.

미결로 두는 이유: 사용자 자격증명을 받아 저장하는 것은 **되돌리기 어려운 보안 결정**이다.
결정 시 반드시 함께 정할 것 — 저장 암호화·범위 한정(테스트 전용 계정 안내)·삭제 경로·
로그 무누출·제3자 앱 로그인(OAuth) 처리. 결정 전까지 **자격증명을 받는 UI를 만들지 않는다.**

### D-6 [LOCKED] zip/패키지 업로드는 이번 스코프에서 제외

현재 지원 소스는 웹사이트 URL · GitHub `owner/repo` · 문서(md/txt/pdf)다. zip을 받으려면
업로드·압축해제·안전 검사·컨테이너 전달이 새로 필요하다. **URL과 리포로 대다수가
커버되며, 이번 재배치는 zip을 나중에 붙이는 것을 막지 않는다.**

### D-7 [LOCKED] 기존 갈래는 유지한다

아이디어 갈래·스펙(붙여넣기) 갈래는 **그대로 둔다.** 이 설계는 코드 갈래(이미 만든 앱)의
진입만 바꾼다. 제거되는 질문은 **삭제가 아니라 뒤로 이동**이며, 사용자가 원하면 여전히
직접 입력·수정할 수 있다.

## 3. 바뀌는 흐름

**지금**
```
갈래선택 → [이름*·빌더·호스팅·데이터·설명·필수동작] → 연결화면 → 소스추가(URL) → 검수
```

**바뀐 뒤**
```
갈래선택 → [주소 또는 리포*] → 1차 검수(즉시) ─┬→ 결과 + "못 본 것" 명시
                                              └→ 의도·스택 추론
                                                   ↓
                              "이 앱은 ~로 보입니다. 맞나요?" (수정)
                                                   ↓
                                   항목 생성 → 정밀 검수 → 고쳐보기 → 빌더팩
```

뒷단(고쳐보기·빌더팩)은 **손대지 않는다** — 이미 라이브다.
